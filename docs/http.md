# Local HTTP API

The optional `server` dependencies expose one versioned API for an opened workspace. The host entry point is `python -m tychora.interfaces.http.server WORKSPACE [--port PORT]`; it binds one Uvicorn worker to `127.0.0.1` and publishes the bound authority in the private `.runtime/endpoint.json` record. `connect_local(WORKSPACE)` verifies that record, the live owner lock, the workspace UUID, protocol version, and the HTTP handshake before returning a blocking client. `Tychora.connect(endpoint, credential, workspace_id)` and `AsyncTychora.connect(endpoint, credential, workspace_id)` are the explicit credentialed client constructors; the async client verifies its handshake before its first operation. A stale record or a different endpoint identity fails closed. The runtime record contains a bearer secret, so its directory and file must remain owner-only. The owner bearer token is persisted in the owner-only `.runtime/owner-token` file and reused across restarts; an unsafe file fails startup with `INTEGRITY_ERROR` rather than being regenerated, and `tychora manage rotate-token` replaces it while the workspace is stopped. Owner-bound continuation cursors still use a per-instance secret and expire with the owner instance. Credentials are sent in `Authorization`, never in URLs; only one-time dashboard launch codes appear in a URL fragment (see below).

`create_app(owner, services, auth)` borrows an already-open owner. Its FastAPI lifespan drains the **current** service binding's accepted source jobs. The server context owns final owner closure, with a fallback drain if startup or shutdown fails. HTTP and the opened workspace's sync/async public Python facades share one `ServiceRuntime` admission gate; an operation pins its service binding through completion. A later settings activation replaces that authoritative binding, and the Python bridge follows the new source scheduler. Embedded transports sharing this owner must enter the same gate and resolve current services per operation; they must not drive a retained `Services` object independently. The host is a local, single-installation-principal service. Separate bearer tokens may have narrower collection, use, read, write, and manage grants; every operation intersects the token grant with the owner's scope and any per-request `X-Tychora-Scope`. Tokens naming a different principal are rejected. Same-principal tokens share that principal's history and idempotency namespace, subject to each token's effective scope and the durable job authorization receipt. This is not multi-user identity isolation.

Every API and MCP request needs exactly one `Host` equal to the bound numeric loopback authority and exactly one `Authorization: Bearer …`. Native clients may omit `Origin`; when present, exactly one Origin must equal `http://` plus that authority. Duplicate control headers are rejected before route parsing. Actual incoming body bytes are limited to 1 MiB, including requests without `Content-Length`; malformed or oversized length is rejected before body parsing. `Last-Event-ID` must be a nonnegative signed 64-bit decimal integer. No wildcard CORS or remote bind is configured. Source paths require write scope and must resolve within configured ingest roots. A request's response or resource-specific bounds may be smaller.

The bundled dashboard is served at /dashboard/. Only GET/HEAD of recognized application routes and real packaged /dashboard/assets/ files may omit bearer authentication. Exact Host and optional Origin admission still apply. Static responses use a restrictive same-origin CSP, no-referrer, frame denial and nosniff; API and dashboard responses use Cache-Control: no-store. Credentials and workspace data are never public static resources. See [dashboard usage](dashboard.md).

### Dashboard launch links

`serve` composes `LocalAuth(..., launch_token=token)` with the owner token, prints one `http://AUTHORITY/dashboard/#launch=CODE` link at startup, and keeps launch codes in memory only: at most eight outstanding (the oldest is evicted), single use, **120 s** expiry, SHA-256 digests compared in constant time, all lost on exit. After 20 failed exchanges within 60 s further attempts get a retryable `WORKSPACE_BUSY` until the window passes. Without `launch_token` (for example the stdio MCP control listener) minting returns 503 and the exchange returns 404.

| Route | Contract |
| --- | --- |
| `POST /v1/session/launch-codes` | Authenticated. Requires `manage` in the effective scope **and** the exact launch credential, so a narrower or different token can never mint a code that yields the owner token. Returns 201 `{code, expires_in_seconds, url}`. `connect_local(...).dashboard_launch_link()` and `tychora manage dashboard-link [--open]` use it. |
| `POST /v1/session/launch` | Unauthenticated exchange of `{ "code": "…" }` (exactly that field, `Content-Type: application/json`, body ≤ 1 KiB) for `{schema_version, token_type: "Bearer", token}`. Exact Host and, when present, exact Origin admission still apply; `Sec-Fetch-Site` other than `same-origin`/`none` is rejected. Other methods get 400. Unknown, expired, reused and malformed codes all get the same 403 `Launch link is invalid or expired.` |

The API returns schema-versioned canonical error envelopes containing `code`, sanitized `message`, and `retryable`; envelopes are under 8 KiB. Invalid requests and budgets use HTTP 400, scope denial 403, missing resources 404, busy/profile/idempotency conflicts 409, removed original 410, unsupported media 406, unavailable capability/index/provider 503, and deadlines 504.

`Idempotency-Key` binds canonical source intent. Duplicate pending submissions return the same durable handle and share one execution; a conflicting intent returns 409. Accepted workers run on the owner's source-job loop independently of the HTTP connection. `GET /v1/jobs/{id}/events` is a reconnectable view of durable events, not a separate execution queue.

Settings activation is exclusive with admitted HTTP and public Python operations and active accepted source jobs. It validates a candidate configuration, including every retained kind in declared collections, and prepares replacement ports inside that exclusive gate. Service constructors require the owner's canonical ports, so preparation temporarily binds the candidate on the owner thread and restores the previous binding in `finally` before any new admission. On success it bumps `policy_epoch` for a changed configuration, atomically replaces `workspace.toml`, then swaps the in-memory owner/store/service binding. This swap is the commit point: later old-bridge cleanup failure or request cancellation cannot report an activation failure. Failed old bridges remain owned for bounded retry and host teardown, with sanitized diagnostics. Invalid or incompatible candidates preserve the previous effective configuration; busy work receives `WORKSPACE_BUSY`. A crash before file replacement may leave an extra epoch invalidation but keeps the old settings file. A crash after replacement recovers the new file on restart; file replacement and the database epoch are not one cross-store transaction. Existing index generations are guarded by representation semantics (embedding settings other than credentials, index backend/settings, and extraction identity), while credential references and reranker edits may change without reinterpreting those generations. The broader `index_fingerprint` remains unchanged for persisted family identity. No provider call or download occurs during activation.

The CLI, Python and MCP surfaces use the same runtime gate. MCP sessions consume the current service binding and close before the host drains accepted source jobs.

Collection names are trimmed and validated; duplicate slugs return a canonical conflict. Listing excludes archived collections unless `include_archived=true`. UUID ordering is pagination order; frontend sorting of a current page is not global name sorting. Policy mutations upgrade strict v1 policies to v2 without a SQL schema migration and increment the policy epoch only when state changes.

`LocalAuth(..., managed_owner_token=...)` is an explicit trusted composition boundary, used by `serve`. Composition requires a managed owner and its exact initial scope, and permits one managed slot per owner. No hidden runtime credential comparison establishes this status. Static tokens never expand, including identical owner clones. The handshake boolean is descriptive and cannot authorize a request; server request state derives identity from authentication. Refresh through a credential-only handshake without an old `X-Tychora-Scope` header after create or consent changes.

Document inventory uses one source page, one selected-revision batch and one channel batch (maximum 400 channel observations). Channel readiness is the canonical recorded batch state, not a new native health probe. Unit/window counts are null with `counts_complete=false`: current exact eligibility requires broader retained ownership/artifact work than this endpoint permits. Recent job lineage is not safely indexed, so `latest_job=null`, `processing_state="unknown"`, and `job_observations_complete=false`. DTOs report the ceilings (5,000 candidate records, 100 jobs, 1 MiB decoded job metadata); this initial implementation performs no unit/job scan and no artifact decoding. Unknown processing state can coexist with published content. Hidden revisions disclose neither their title, media nor size; unavailable size is null. Exact paginated content inspection remains separate.

## Guided administration endpoints

All of the following require full canonical workspace management authority, even
when an `X-Tychora-Scope` header selects fewer collections:

| Method | Path | Body / result |
| --- | --- | --- |
| GET | `/v1/settings/fields` | `SettingsFieldView` with exact base digest |
| POST | `/v1/settings/preview` | `SettingsPatch` → redacted `SettingsPreview` |
| PATCH | `/v1/settings` | `SettingsPatch` → refreshed `SettingsFieldView` |
| GET | `/v1/models` | `ModelCatalog` |
| POST | `/v1/models/setup-plan` | `{selections: string[]}` → existing `ModelAssetPlan` |
| GET | `/v1/models/readiness?selection=...` | Repeat selection for up to four assets selections → `ModelReadiness` |

PATCH and expert PUT settings use exclusive admission; preview is read-only.
Ordinary GET settings remains redacted. There is no new model activation,
download, backup or rebuild executor: explicit setup uses POST jobs as before.
See configuration and operations documentation for field validation, historical
verification evidence, request budgets and compatibility failures.
